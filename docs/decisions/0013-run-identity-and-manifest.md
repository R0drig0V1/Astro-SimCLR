# 0013: Run identity, the run manifest and retention

- **Status:** accepted (2026-11-08, phase 4, task A0)
- **Implemented by:** `src/astro_simclr/runs/` (`canonical.py`, `identity.py`,
  `manifest.py`, `layout.py`); the numerics line of `.github/pull_request_template.md`
- **Checked by:** `tests/test_runs_canonical.py` (with the pinned
  `tests/fixtures/runs/canonical_configs.json`, regenerated by `tests/_canonical_cases.py`),
  `tests/test_runs_identity.py`, `tests/test_runs_manifest.py`, `tests/test_runs_layout.py`

## Context

Phase 4 replaces the hand-written tmux queues and the `~/runs` directories with a run
registry (A2) and a durable queue (A3), and later with a new engine (track B). All three
need to answer "is this the same run?" before anything is trained, and "what was this
run?" afterwards, and they must agree. Review round 1 of the phase (findings F2, F3, F14)
rejected a content-addressed "never repeat" key: identical configs are rerun on purpose
(protocol 2.3's confirmatory rerun; GPU non-determinism), a commit that changes no numerics
must not make every run new, and one that does change them must. The interfaces are frozen
first (A0) so that A1-A3 and 4.2 can build on them in parallel.

## Decision

1. **The canonical semantic config.** The hashed document is
   `{"canonical_version": 1, "command": ..., "settings": {...}}`, where `settings` is the
   resolved `Settings` (defaults materialised) without the non-semantic and identity keys.
   Its canonical JSON has sorted keys, no whitespace, ASCII escapes, `repr` floats (the
   shortest exact form), one zero (`-0.0` is `0.0`), ints distinct from floats
   (`limit_train_batches: 2` is batches, `2.0` a fraction) and no NaN or infinity. The
   **config hash** is its SHA-256. The training subcommand is part of it: one `Settings`
   means different runs under `linear-eval` and `fine-tune`.
2. **The excluded keys are a coded list with a reason each** (`NON_SEMANTIC_KEYS`):
   `accelerator` (the device used is the machine class), `data_dir` (the content is the
   data SHA-256), `output_dir`, `num_workers`, `checkpoint_every_n_steps` (writing a
   checkpoint draws no random numbers) and `progress_bar_refresh_rate` (display only).
   Every other field is semantic, including the ones a subcommand does not read (`encoder_name` of a supervised
   run): an unclassified or unused key can only make two equal runs look different, never
   two different runs look equal.
3. **`num_workers` is non-semantic, with a caveat.** On the legacy CPU-worker path,
   Lightning seeds each DataLoader worker, so another worker count draws other
   augmentations. That is a different draw of the same distribution, the same class of
   difference as GPU non-determinism, so it gives a new attempt, not a new run. The
   `carrasco2021` schedule (every phase-2 and 2.5 run) requires 0, so the question does not
   arise there, and the manifest records the value.
4. **Identity keys are hashed in the run id, not in the config hash** (`IDENTITY_KEYS`):
   `seed`, so that the seeds of one arm share a config hash, and `pretrained`, a path whose
   content, not its location, is what matters.
5. **Run id** = SHA-256 of the canonical JSON of `RunIdentity`: the config hash, the seed,
   the split (a fold, `"screen"`, or none), the data SHA-256, the splits file's SHA-256, the
   pretrained checkpoint's SHA-256, the machine class, the engine and `numerics_epoch`. Two
   of these are additions to the plan's list. The pretrained checkpoint: without it, two
   evaluations of different encoders would share an id. The engine: a plain-engine run must
   never pass for an attempt of a Lightning run (plan A1 compares a new-engine variant only
   with a baseline rerun on the new engine, and 4.7(c) needs the two apart). The **attempt** counter is recorded next to the id and names
   the run directory, never the id. The git SHA, the dirty flag and `uv.lock` are recorded,
   not hashed.
6. **The data SHA-256 is computed from `meta.json`, not from the raw bytes**: the canonical
   JSON of the kind, the source pickle's SHA-256 and each split's size and array-file
   SHA-256s. For a `raw-alerts` pool (ADR 0012), it is the kind, the schema (which holds
   the label names), the size and the array-file SHA-256s; its `source` is free-form
   provenance. It is not the file's own hash because `meta.json` holds `created_by` (the
   package version), and a version-1 layout has the same arrays as a uint8-only version-2
   one. A layout that gains `images_f32.npy` hashes differently: it has more content.
7. **The machine class** is a slug. By default, CUDA devices are classed by GPU model
   (`cuda-nvidia-geforce-gtx-1050`) and CPU and MPS devices by ISA (`cpu-x86_64`,
   `mps-arm64`). An experiment spec (A3) may name its own.
8. **`numerics_epoch`** is the integer `runs.identity.NUMERICS_EPOCH` (1 now). A PR bumps
   it when it changes what an existing config computes on an existing machine class: an
   augmentation fix (C7's rotation order would have bumped it), another operation order or
   random-number consumption, a default precision, a torch / torchvision / CUDA wheel
   change in `uv.lock`, or a pixel moved by the data pipeline. A new flag whose default
   reproduces the old behaviour does not bump it, and neither does a bit-exact refactor.
   The PR template asks every PR.
9. **Keeping hashes stable as `Settings` grows.** A field added later, whose default
   reproduces the old behaviour, goes in `HASH_NEUTRAL_DEFAULTS` with that value, and is
   left out of the canonical form at it. Old hashes (and old manifests) stay valid. Any
   other change of the canonical form moves the pinned fixture hashes and fails a test.
   It must then regenerate the fixture and say so in its PR; a change of the rules bumps
   `CANONICAL_VERSION`.
10. **The contract for the nested config (task 4.2).** The hash is defined on the *flat
    view*, the plain mapping keyed by today's `Settings` field names. A nested config
    proves hash equality by lowering itself to that view, filling the keys it does not have
    with the flat defaults, then calling `semantic_config_from_plain(command, view)`.
    `complete=True` refuses a forgotten or invented key. The test then compares the result
    with the flat preset's hash; `semantic_diff` names the keys that differ. The flat view
    remains the definition of the hash after `Settings` itself is retired.
11. **`manifest.json`, format version 1.** It holds: run id, attempt, command, the full
    config as run, the config hash and `canonical_version`, the identity, git
    `{sha, dirty}`, the `uv.lock` SHA-256, `machine` (`device`, `gpu`, `torch`, `cuda`,
    `fp32_precision` per ADR 0010, with extra keys allowed), `engine` (`lightning` or
    `plain`, equal to the identity's), named `seeds`, `concurrent_jobs`, `status` and
    ISO-8601 UTC timestamps.
    Statuses go `queued → running | cancelled` and
    `running → finished | failed | cancelled | queued`. Going back to `queued` is an
    expired lease, and the attempt resumes. Only `finished` is finished. The reader
    validates the exact key set (a repeated key is an error), every type (`true` is not 1)
    and the consistency of the status and timestamps, of `pretrained` with its SHA-256 and
    of the engine with the identity's. A garbled file is a `ManifestError` too. It also recomputes the config hash from the recorded config mapping (not
    through today's `Settings`, so old manifests stay readable) and the run id from the
    identity, and refuses a mismatch.
12. **Run directory and retention.** One attempt per directory,
    `<run id[:16]>-a<attempt>`, holding: `manifest.json`, `metrics.json`,
    `scalars.jsonl`, `tb/`, `predictions_*.npz` and `ckpt/{last,best}.pt`. Lightning runs
    keep `checkpoints/{last,best}.ckpt` and `lightning_logs/` until 4.8. Retention is a
    pure function `retention(manifest, artefacts)`:
    - an unfinished attempt keeps everything;
    - a finished one deletes `last`, and keeps `best` only for `pretrain`;
    - records, results, logs, figures and unknown files are kept forever.

    Nothing deletes files yet.

## Consequences

- A1 calls `run_identity`, `new_manifest`, `transition` and `write_manifest` from
  `run_command`. A2 indexes manifests by run id and config hash, and A3 expands specs into
  run ids before anything runs. None of them redefines identity.
- Changing an unused setting (for example `encoder_name` on a supervised run) gives a new
  run id. The cost is a missed match, never a false one. A command-aware projection would
  change the canonical form, so it would bump `CANONICAL_VERSION`.
- A torch upgrade without a `numerics_epoch` bump would mark the new runs as attempts of
  the old ones. The PR template line and review are the guard; `uv_lock_sha256` in the
  manifest shows it after the fact.
- The reader does not check that a manifest sits in the directory its run id and attempt
  name: today's runs write to a user-chosen `--output-dir`. The queue (A3), which names
  the directories, can add the check.
- The run directory name uses 64 bits of the id, so a collision is negligible at this
  scale, and the manifest holds the full id for verification.
- Revisit `num_workers` if a worker-dependent result ever has to be reproduced exactly
  (the plain engine's data tiers draw on the device, without workers).
